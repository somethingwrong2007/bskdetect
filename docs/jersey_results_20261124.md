# 球衣号码识别 · 结果报告（合成基线，2026-11-24）

**环境**：Windows 10.0.26100 / CPU 推理（onnxruntime 1.32 CPUExecutionProvider，**无 TensorRT**）
**权重**：`data/models/jersey_small.onnx`（0.079M 参数，输入 `1×3×64×96`，输出 22 logits）
**数据**：合成（`bsk/jersey_synth.py`，训练 seed 11 / 留出 seed 991）
**产物**：`bsk/perceive/jersey.py`、`bsk/jersey_synth.py`、`bsk/train_jersey.py`、
`eval_jersey.py`、`test_jersey.py`、`bsk/server_rt.py` 接入、`docs/jersey_usage.md`

> **本页数字都是合成集上的，不是验收数字。** 需求 §6 的 ≥90% / ≥95% 必须用真实标注裁片
> （`--mode manifest`）和真实视频（`--mode video`）重测；本机 `data/raw` 为空、无人工标注，
> 这两项跑不了。下表把「能判定」和「不能判定」分开写清楚。

## 1. 对照验收标准

| 指标 | 目标 | 本次合成实测 | 判定 |
|---|---|---|---|
| 单帧可读裁片 top-1 | ≥ 90% | **89.0%**（留出集 600 张，可读 300 张） | 合成接近达标；真实未测 |
| 轨迹级最终号码准确率 | ≥ 95% | **92.3%**（40 条仿真轨迹里 26 条发布） | 不能判定（仿真，非真实轨迹） |
| 每条轨迹号码切换次数 | ≤ 1 | **最大 1**，均值 0.05；单测 12 组覆盖配额/锁定 | ✅ 通过 |
| 高置信错号（conf>0.6 且错） | < 2% | **6.8%** | ❌ 未达标，见 §3.3 |
| 新增延迟（平均/帧） | ≤ 2 ms | **0.10–0.36 ms** 均值，p95 0.42–1.14 ms（CPU，未用 TRT） | ✅ 通过（真实 GPU 数仍待测） |
| 960 宽仍 ≥ 30 fps | 不回退 | 未测 | 需要 `data/raw` + 服务端 |
| 读不出保持 `None` | 不瞎猜 | blank_recall **0.993**，空白误判成号码 **0/300** | ✅ 通过 |

训练内验证（同分布划分）val_top1 = 0.892、blank_recall = 1.000；**留出集 0.890** 说明没有靠
背题虚高。十位级准确率 0.933、个位级 0.937。

## 2. 延迟与吞吐

| 场景 | 均值 | p95 |
|---|---|---|
| 单裁片前向（batch 32，CPU） | 0.190 ms | 0.236 ms |
| 融合仿真整帧新增（40 轨迹 × 90 帧） | 0.085–0.361 ms | 0.414–1.137 ms |

整帧口径已经把「裁图 + 门控 + 采样节拍」都算进去了（`crop_ms` 累计 9.7–14.9 ms / 710 张裁片）。
两次运行均值差 3.5 倍是因为前一次机器上还有训练在跑 —— **CPU 上余量已经够 2ms 预算，但上线
数仍需在目标机用 TRT 实测**，`[WARN] Frame … jersey=Xms` 会直接把这一项打出来。

## 3. 失败案例分析

**3.1 融合层是「弃权换准确」，不是「纠错」。** 把可读帧占比从 0.55 提到 1.00（其余参数不变）：

| 可读帧占比 | 发布率 | 发布后准确率 | 首次发布中位帧 | 切换上限 |
|---|---|---|---|---|
| 0.55 | 0.650 | 0.923 | 28 | 1 |
| 0.80 | 0.825 | 0.818 | 16 | 1 |
| 1.00 | 0.825 | 0.758 | 16 | 1 |

看得越清楚，发布得越多、**但越容易把持续错号发出去**：裁片级 11% 的错误如果是稳定的
（同一件球衣帧帧都错成同一个号），EMA 只会反复确认它，攒够 0.6 就发布并锁死。结论很直接：
轨迹级 ≥95% 基本由裁片精度决定，时序融合能防闪烁（切换 ≤1 是真的），不能替代精度。

**3.2 未发布轨迹卡在 `min_conf`，不是卡在 `min_obs`。** 14 条未发布轨迹的观测次数都是 18
（采样节拍给满了），但融合后验最高只有 0.036–0.423，空白 EMA 0.539 —— 空白票把号码后验直接
置零，可读帧不到 60% 时几乎发不出号。**如果真实素材上发布率太低（面板长期空号），先动
`min_conf` 或把空白票改成乘性衰减，不要动 `every_n`**（动它只会让每条轨迹观测更少，改不了
后验聚不起来这件事）。

**3.3 高置信错号 6.8% 超目标 3 倍。** 合成集的字体/增广分布太窄，模型在没有真实噪声的分布上
过拟合出了过度自信。这一项**不能靠调阈值修**：阈值只决定发不发，不改变「已发布里错号占比」。
需要的是真实标注裁片微调（`--finetune` + `--manifest`），必要时加温度校准。

**3.4 错误不集中在字形对上，说明是信噪比问题不是混淆问题。** 最大单一混淆是十位 8→3（3/300），
个位 9→2、2→4 各 2/300，其余散布。含义：专门给 3/8 做增强收益很低，**预算应该花在真实样本量上**。

**3.5 门控与空白侧目前干净。** 几何自检 200/200：正面裁片全保留、侧身（肩宽占框 0.05）全拒绝、
14×30 的过小框全拒绝；空白没有误报成号码。需求 §3.3「不瞎猜」这条成立。

## 4. 单元与一致性验证

`python test_jersey.py` → 12 组用例全部通过（裁片几何、骨架门控、头解码与双射、发布门限、
切换配额与锁定、轨迹丢失重置与跨视频隔离、同队冲突打折、读不出留 `None`、采样节拍与
`max_crops`、权重缺失 no-op、sidecar 尺寸守卫、ONNX 与 torch 数值一致性 **max|Δ| = 0.0000**）。
其中「配额用完不锁定」和「空场后状态永不回收」两个真实缺陷是这组用例逼出来的。

## 5. 还没做 / 不能在本机做的

1. **真实标注裁片评估**（`--mode manifest`）—— 需要 M1 采片 + 人工填 300–800 个 label。
   这是唯一能证明 ≥90% 的路径，也是 §3.3 高置信错号的修法。
2. **真实轨迹评估与端到端帧率**（`--mode video`）—— 需要 `data/raw/harden_55.mp4`、RTMO 权重、
   `av` 依赖；本机 `data/raw` 为空，本次该模式按预期 `skipped`。
3. **TensorRT/GPU 延迟实测**（固定 profile `1×3×64×96` 的 min/opt/max）与 CUDA 12 训练轮子
   （本机是 cu118 + sm_120，训练自动降级 CPU，导出与推理不受影响）。
4. **门控阈值标定** —— `min_shoulder_frac=0.16` 目前是推理侧的合理猜测，需在真实标注上跑
   `--mode gating` 看误杀率。
